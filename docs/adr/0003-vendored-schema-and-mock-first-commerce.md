# ADR 0003 — Vendored schema, generated types, mock-first commerce

**Classification: INTERNAL**

- **Status:** Accepted
- **Date:** 2026-08-28
- **Decides:** where `@sentra/sdk-commerce`'s types come from, and how M3's demo runs
  without a live Shopify store or a network connection.

## Context

`@sentra/sdk-commerce` needs TypeScript types that genuinely match Shopify's Storefront
GraphQL schema — a hand-drifted type is worse than none, because it compiles cleanly while
lying about the shape of a response. At the same time, the demo this SDK serves (M3's
`apps/storefront`) must run in front of an audience with no live store and no network: a
conference Wi-Fi outage or a Shopify partner-store rate limit cannot be allowed to end the
demonstration.

Both constraints point away from the obvious approach — introspecting a real store at build
time — and toward vendoring a schema and mocking every request against it.

## Decision

Vendor the published Storefront API introspection schema from `@shopify/hydrogen-react`
(Shopify's own package, built for exactly this purpose) into the repository as
`packages/sdk-commerce/schema/storefront.schema.json`. Generate TypeScript types and typed
query strings from that committed file with `graphql-codegen`. Build every SDK operation —
products, collections, cart — against MSW fixtures, so the SDK's own contract tests and the
storefront's dev/demo builds never touch a real endpoint.

## Consequences

- `packages/sdk-commerce/schema/storefront.schema.json` is a 771 KB JSON file committed to
  the repository — large for a text diff, but reviewable, unlike a schema that changes
  invisibly underneath the codebase.
- Moving to a newer Storefront API version requires running
  `pnpm --filter @sentra/sdk-commerce sync-schema`, which re-vendors the schema and rewrites
  its provenance record. This is a deliberate, visible step rather than something that
  happens automatically on `pnpm install`.
- A checksum test (`version.test.ts`) guards against the schema file being hand-edited
  rather than regenerated by `sync-schema`: it recomputes the committed file's SHA-256 on
  every test run and asserts it matches `schema/PROVENANCE.json`.
- `SchemaError` (the `kind: 'schema'` branch of `StorefrontError`) gains real operational
  meaning: because the generated types come from a pinned, vendored schema, a response that
  fails to match them means the *live* schema has drifted from the one this SDK was
  generated against — an operational signal to alert on, not a user-facing failure to
  retry.
- The demo runs fully offline: `apps/storefront`'s mock build and `@sentra/sdk-commerce`'s
  own contract tests both run against the same MSW fixture set, so nothing about the demo
  depends on Shopify's infrastructure being reachable.

## Alternatives not taken

1. **Introspect a live store at build time.** Rejected: the build would depend on network
   access and on a particular store's continued availability, and schema drift would become
   invisible — types would silently change under the codebase rather than showing up as a
   reviewable diff.
2. **Hand-write the types.** Rejected: this directly contradicts the requirement that types
   be generated from the published schema rather than asserted by a developer, and the
   vendored schema describes 424 types (per `codegen.ts`'s own accounting) — far past what
   a person can keep synchronised with Shopify's API by hand without silent drift.
3. **Use `@shopify/storefront-api-client` for transport, instead of building
   `transport.ts`.** Rejected here, and honestly: this is a genuine trade-off, not a
   strawman. Shopify's own client is maintained, handles the GraphQL-over-HTTP mechanics
   correctly, and adopting it would have meant less code in this repository — the same
   "adopt where the problem is solved" reasoning `packages/ui/README.md` already applies to
   `focus-trap` and `@tanstack/vue-virtual`. What it would not have given this project is a
   transport whose timeout, bounded-retry, and cost-tracking behaviour is *this repository's
   own*, reviewable, and testable without a socket. `retryDelayMs`'s deficit arithmetic
   (waiting exactly as long as the reported cost budget needs to refill, not a guessed fixed
   interval) and the throttle/network/schema error split in `errors.ts` are the layer this
   milestone was built to demonstrate — wrapping someone else's client would have made that
   layer a thin pass-through with nothing of our own to show or test. The honest cost of
   this decision is real, though: `transport.ts` is code this repository must maintain,
   test, and keep correct against Shopify's actual throttling behaviour, in perpetuity,
   that `@shopify/storefront-api-client` would have carried instead.

## Verification

- `packages/sdk-commerce/src/version.test.ts` — recomputes the committed schema file's
  checksum and asserts it against `PROVENANCE.json`, and asserts the schema contains the
  types the operations layer depends on (`QueryRoot`, `Product`, `Collection`, `Cart`,
  `CartUserError`).
- `packages/sdk-commerce/src/mocks/contract.test.ts` — exercises collection listing,
  product detail, and the full cart lifecycle against the MSW fixtures, and its `failure
  scenarios` block drives all four `StorefrontError` taxonomy members (`throttled`,
  `network`, `graphql_user`, `schema`) to confirm each is actually reachable, not just
  declared in a type.
- `packages/sdk-commerce/src/sanitize.test.ts` — 18 cases against `jsdom` covering removal
  of `<script>` elements, inline event handlers, `javascript:` URLs, `<iframe>`s, `style`
  attributes, and form controls; `data:`-URI image stripping (including a case-and-
  whitespace variant); reverse-tabnabbing hardening on `target="_blank"` links; idempotency
  on already-sanitised output; and the environment self-test that makes the module fail
  closed rather than silently pass unsanitised HTML through under a DOM implementation that
  cannot actually sanitise (`DOMPurify.isSupported` reporting `true` is not sufficient
  evidence — measured directly against `happy-dom`).
- `apps/storefront/e2e/smoke.spec.ts` — the Playwright smoke run against the production
  build, the only place any of this is proven in a real browser rather than `jsdom`: it
  confirms a script embedded in a hostile product description never executes and no
  `<script>` element survives into the rendered DOM.
